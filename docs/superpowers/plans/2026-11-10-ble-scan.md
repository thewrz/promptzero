# BLE discovery implementation plan

Goal: expose bounded BLE advertisement discovery and allowlisted diagnostic CLI
in both forks while preserving existing filters, risk gates, and fork features.
Spec: ../specs/2026-11-10-ble-scan-design.md

## Client contract

- Keep wire validation in the Marauder client and tool registration in `wifi_ble.go`.
- Accept `all` and the existing `airtag`, `flipper`, `flock`, and `meta` filters.
- Hold the serial connection through preparation, collection, and cleanup.
- Read beyond the startup prompt; advertisements arrive asynchronously.
- Bound output and scan duration. Drain queued input before stop confirmation,
  report unsettled input, and retain a separate two-second cleanup budget.
- Install cleanup before the start write and terminate a partially written
  command before sending stopscan.
- Allow only `help`, `info`, `stopscan`, `sniffbt`, and the four filtered forms
  through `wifi_read_cli`; reject extra whitespace, chaining, and control characters.
- Tool durations are whole seconds from 1 to 60, default 30. Preserve those
  numeric limits and defaults in MCP discovery schemas.
- Describe active scan requests explicitly. Established Bluetooth connections
  and audio decoding are outside this feature.

## Hardware evidence

A bounded trial on the ESP32-C5 / Marauder v1.10.2 demonstrated startup,
collection duration, cleanup, and a subsequent working `info` command. The
normal service was restored. No advertisements appeared during that trial,
so positive reception from a known advertiser remains unverified and the
hardware-validator skip is retained. No captures are stored in either repo.
